# SPORA

**Личная экосистема для заметок, задач, настроения, здоровья и питания.**

SPORA — русскоязычное веб-приложение на React с локальным хранением в IndexedDB, синхронизацией с PostgreSQL через Express API и service worker для PWA и push-уведомлений. Текущая версия в `package.json` — `0.1.0`.

Приложение рассчитано на личное использование: вход по одному общему паролю, без регистрации и разделения данных между пользователями. Учёт здоровья и напоминания не заменяют медицинские рекомендации и не гарантируют своевременную доставку уведомлений.

## Возможности

| Раздел | Возможности | Маршрут |
| --- | --- | --- |
| Главная | Сводка настроения, задач и тренировок за сегодня, напоминание о лекарствах | `/home` |
| Настроение | Оценка от 1 до 5, эмоции, комментарий, история и диаграмма последних записей | `/mood` |
| Идеи и задачи | Заметки с цветами, тегами, закреплением и кластерами; задачи с приоритетами, статусами и сроками; связи и зависимости; поиск, список, календарь, граф и карта | `/notes` |
| Детали записи | Просмотр и редактирование заметки или задачи по UUID | `/notes/:uuid`, `/tasks/:uuid` |
| Тренировки | Журнал занятий с типом, длительностью и заметкой | `/workout` |
| Цели | Категории, прогресс, промежуточные шаги и завершение целей | `/goals` |
| Здоровье | Учёт веса, список лекарств, дозировки, расписание и отметки приёма; настройка уведомлений | `/health` |
| Питание | Рецепты и ингредиенты, продукты в холодильнике с количеством и единицами, недельный план питания | `/recipes` |
| Вход | Авторизация по паролю владельца | `/login` |

`/` перенаправляет на `/home`, `/planning` — на `/notes`. Разделы приложения требуют входа.

Для заметок можно сохранять геопозицию. Карта использует Leaflet; определение названия места выполняется через Nominatim при доступной сети. При ошибке обратного геокодирования сохраняются координаты.

Клиент сначала работает с локальной базой, затем отправляет изменения серверу. PostgreSQL хранит серверную копию данных; IndexedDB — локальные записи и очередь отправки. API не раздаёт клиентскую сборку.

```text

  shared/
    api/        # HTTP-клиент, синхронизация, outbox, Gemini
    db/         # Схема Dexie
    lib/        # Локальные уведомления и push-подписки
    types/      # Общие типы
    ui/         # Общие UI-компоненты
    test/       # Настройка тестового окружения
```

Алиасы импортов: `@app`, `@pages`, `@widgets`, `@features`, `@entities`, `@shared`. Они настроены в TypeScript, Vite и Vitest.

## Требования

- **Node.js 22 или новее**, рекомендуется актуальная LTS-версия. В lock-файле `concurrently` требует Node.js `>=22`.
- **npm** для установки зависимостей из `package-lock.json`.
- **PostgreSQL** с созданной базой и ролью, имеющей права на создание и изменение таблиц. Минимальная версия PostgreSQL в проекте не зафиксирована.
- Современный браузер с IndexedDB. Для Web Push нужны поддержка Push API, service worker и разрешение пользователя.
- HTTPS при публикации приложения; `localhost` подходит для локальной разработки service worker.

## Быстрый старт

Все команды ниже, кроме SQL, выполняются из корня репозитория.

### 1. Установка зависимостей

```sh
npm ci
```

Корневой `package.json` содержит и клиентские, и серверные зависимости. Для этого способа запуска отдельный `npm install` в `server/` не требуется. У сервера также есть собственный `package.json`, но его диапазоны версий отличаются от корневых; основной сценарий здесь использует корневой lock-файл.

### 2. Создание PostgreSQL-базы

Подключитесь к PostgreSQL под администратором и выполните, заменив пароль:

```sql
CREATE ROLE spora WITH LOGIN PASSWORD 'replace-with-a-strong-password';
CREATE DATABASE spora OWNER spora;
```

Таблицы создаются автоматически сервером. Отдельной команды миграции нет.

### 3. Настройка окружения

Создайте в корне `.env` с клиентскими параметрами:

```dotenv
VITE_SERVER_URL=http://localhost:3003
# Необязательно: AI-модуль не подключён к текущим страницам.
# VITE_GEMINI_API_KEY=your-key
```

Создайте `server/.env`:

```dotenv
DATABASE_URL=postgresql://spora:replace-with-a-strong-password@localhost:5432/spora
AUTH_PASSWORD=replace-with-a-strong-login-password
JWT_SECRET=replace-with-a-long-random-secret
PORT=3003
VAPID_EMAIL=admin@example.com
# Для push добавьте пару VAPID_PUBLIC_KEY / VAPID_PRIVATE_KEY.
```

Общий список параметров есть в [`.env.example`](.env.example). Не копируйте адрес сервера из примера без изменения: для локального запуска используйте свой backend.

Сгенерировать JWT-секрет можно командой:

```sh
node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"
```

Если пароль PostgreSQL содержит специальные символы URL, закодируйте их в `DATABASE_URL`.

### 4. Запуск сервера и клиента

Первый терминал:

```sh
node --env-file=server/.env server/index.js
```

Второй терминал:

```sh
npm run dev
```

Откройте `http://localhost:5173` и введите пароль из `AUTH_PASSWORD`. Если порт занят, Vite может выбрать следующий — проверьте адрес в выводе команды.

**Почему явный `--env-file`:** `server/db.js` создаёт PostgreSQL-пул при импорте, до выполнения `config()` в `server/index.js`. Поэтому при запуске из корня одного `server/.env` недостаточно для гарантированной передачи `DATABASE_URL` в пул. Предварительная загрузка через Node.js устраняет эту зависимость от порядка импортов без изменения кода.

Для автоматического перезапуска backend используйте:

```sh
node --env-file=server/.env --watch server/index.js
```

`npm run dev:all` также запускает оба процесса, но требует, чтобы `DATABASE_URL` уже был доступен процессу — через окружение либо корневой `.env`. Остальные серверные параметры загружаются из `server/.env`; уже заданные переменные dotenv не переопределяет.

### 5. Проверка доступности

```sh
curl http://localhost:3003/health
```

Ожидаемый ответ: `{"ok":true}`. Это проверка HTTP-процесса, **не готовности PostgreSQL**. Дополнительно проверьте вход и создание записи, а для проверки синхронизации — её появление в другом браузере после входа.

При разделённых адресах клиента и API обычные данные используют `VITE_SERVER_URL`, но push требует отдельной настройки: см. [PWA и уведомления](#pwa-и-уведомления).

## Переменные окружения

### Клиент: корневой `.env`

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `VITE_SERVER_URL` | Базовый адрес обычных API-запросов, без завершающего `/` | Пустая строка: запросы на `/api` текущего origin |
| `VITE_GEMINI_API_KEY` | Ключ для вызова Gemini из браузера | Не задан; вызов AI без ключа завершится ошибкой |
| `VITE_VAPID_PUBLIC_KEY` | Необязательный публичный VAPID-ключ для push | Получение через `/api/push/vapid-public-key` |

`VITE_VAPID_PUBLIC_KEY` используется кодом, но не включён в `.env.example`. Значения `VITE_*` попадают в клиентскую сборку: **они не являются серверными секретами**. После изменения перезапустите Vite, а для production пересоберите клиент.

### Сервер: `server/.env` или окружение процесса

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | Строка подключения PostgreSQL | Проект не задаёт; при отсутствии `pg` использует собственные настройки подключения |
| `AUTH_PASSWORD` | Общий пароль входа | Нет |
| `JWT_SECRET` | Секрет подписи и проверки JWT | Нет |
| `PORT` | HTTP-порт | `3003` |
| `VAPID_PUBLIC_KEY` | Публичный ключ Web Push | Нет |
| `VAPID_PRIVATE_KEY` | Приватный ключ Web Push | Нет |
| `VAPID_EMAIL` | Контактный email VAPID | `admin@spora.app` |

Не используйте одинаковые значения для пароля входа, пароля БД и JWT-секрета.

## Хранение и синхронизация

### Локальные данные

Dexie использует IndexedDB-базу `spora`. В ней находятся `moods`, `notes`, `tasks`, `workouts`, `goals`, `weights`, `medicationLogs`, `medications`, `recipes`, `fridge`, `mealPlan` и `outbox`.

Локальный ключ записи — числовой `id`, идентификатор для синхронизации — UUID. Токен входа хранится отдельно, в `localStorage` под ключом `spora_token`.

### Обмен с сервером

1. Изменение сохраняется локально, затем отправляется API.
2. При повторяемой ошибке операция помещается в IndexedDB-очередь `outbox`.
3. При запуске с токеном выполняются постановка старых локальных данных в очередь, отправка очереди и получение `/api/sync`.
4. Полученные серверные записи добавляются или обновляются локально по UUID, после чего хранилища перечитываются.

Очередь отправляется при доступной сети и токене, в том числе после события `online` и возвращения вкладки в видимое состояние. Операции над одной записью схлопываются; удаление вытесняет накопленные изменения.

**Ограничения:**

- Это не система разрешения конфликтов: при совпадении UUID серверная запись обновляет локальную; автоматического выбора по `updatedAt` нет.
- Повторяемыми считаются сетевые ошибки, HTTP `401`, `408`, `429` и `5xx`. После восьми неудачных попыток операция удаляется из очереди; неповторяемая ошибка также приводит к удалению операции.
- Наличие локальных записей не означает, что они уже сохранены на сервере. Очередь не гарантирует бесконечное хранение и доставку.
- Первый вход требует работающего API. Нельзя обещать полную работу приложения без сети: локальные данные сохраняются, но вход, синхронизация, внешние карты и push зависят от сети и состояния кэша.
- Синхронизация при запуске не равнозначна постоянному realtime-обмену между устройствами.

### Серверные данные

`server/db.js` создаёт таблицы PostgreSQL через `CREATE TABLE IF NOT EXISTS` и добавляет отдельные поля через `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`. Отдельной системы версионируемых миграций и rollback нет.

Доменные таблицы соответствуют локальным коллекциям, но используют имена `medication_logs` и `meal_plan`; дополнительно есть `push_subscriptions`. Структурированные поля, например теги, ингредиенты и расписания, хранятся в JSONB.

## API

Базовый адрес в локальном примере: `http://localhost:3003`.

### Вход и доступ

```http
POST /api/login
Content-Type: application/json

{"password":"your-login-password"}
```

При успехе возвращается JSON с `token`. JWT действует **90 дней**. Регистрации, отдельных учётных записей и разграничения доступа к данным нет.

Для защищённых запросов передавайте:

```http
Authorization: Bearer <token>
```

### Основные маршруты

| Метод | Путь | Доступ и назначение |
| --- | --- | --- |
| `GET` | `/health` | Публичный; доступность HTTP-процесса |
| `POST` | `/api/login` | Публичный; получение JWT по паролю |
| `GET` | `/api/sync` | JWT; получение всех доменных коллекций |
| `GET` | `/api/push/vapid-public-key` | Публичный; ответ `{ "key": "..." }` |
| `POST` | `/api/push/subscribe` | JWT; сохранение push-подписки с часовым поясом |
| `DELETE` | `/api/push/subscribe` | JWT; удаление подписки по `endpoint` |
| `POST` | `/api/push/test` | JWT; тестовая отправка всем подпискам |

Доменные ресурсы: `moods`, `notes`, `tasks`, `workouts`, `goals`, `weights`, `medication-logs`, `medications`, `recipes`, `fridge`, `meal-plan`.

- `POST /api/<resource>` — upsert записи по UUID.
- `DELETE /api/<resource>/:uuid` — удаление.
- `PUT /api/<resource>/:uuid` — частичное обновление для `notes`, `tasks`, `goals`, `recipes`, `fridge`.
- Чтение коллекций выполняется через `/api/sync`, а не отдельные `GET` каждого ресурса.

Поля запросов и преобразования данных описаны кодом в [`src/shared/types/`](src/shared/types/), [`src/shared/api/server.ts`](src/shared/api/server.ts) и [`server/routes/data.js`](server/routes/data.js). Отдельной OpenAPI-спецификации нет.

При недоступной БД маршрутизатор данных может вернуть `503`. Ошибка чтения отдельной таблицы в `/api/sync` логируется сервером и заменяется пустой коллекцией — ответ синхронизации может оказаться частичным.

## PWA и уведомления

Production-сборка создаёт manifest и service worker из `src/sw.ts` через стратегию `injectManifest`. Workbox предварительно кэширует собранные ресурсы. Новая версия service worker активируется без ожидания закрытия всех вкладок.

### Настройка Web Push

Сгенерируйте ключи:

```sh
npx web-push generate-vapid-keys
```

Сохраните пару в `server/.env` как `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY`, задайте `VAPID_EMAIL` и перезапустите сервер. Приватный ключ нельзя переносить в `VITE_*`.

Для проверки используйте production-сборку через HTTPS или localhost, разрешите уведомления в браузере и включите подписку в разделе здоровья. Dev-конфигурация Vite не включает `devOptions.enabled` для PWA.

**Важно о маршрутизации:** функции push в `src/shared/lib/pushSubscription.ts` вызывают относительный `/api/push/...` и не используют `VITE_SERVER_URL`. Публичный ключ можно задать через `VITE_VAPID_PUBLIC_KEY`, но это не меняет адрес запросов подписки. Для работающего push проксируйте `/api` с origin клиента на backend. В текущем `vite.config.ts` такого dev-прокси нет.

Серверный планировщик проверяет расписания активных лекарств каждые 30 секунд. Он учитывает дни недели и часовой пояс подписки; пустой список дней означает ежедневный приём. Планировщик запускается только после успешной инициализации БД при старте процесса.

Есть также локальные уведомления через таймеры страницы. Они зависят от работы вкладки и ограничений браузера; их нельзя считать надёжной заменой серверному push. Локальный таймер перебирает время приёма, но не проверяет дни недели, в отличие от серверного планировщика.

Дедупликация серверных напоминаний находится в памяти процесса. Несколько экземпляров API или перезапуск в текущую минуту могут привести к повторной отправке. Закрытая вкладка сама по себе не отключает Web Push, но доставка зависит от браузера, ОС и push-сервиса.

Manifest, HTML и уведомления ссылаются на `/icons/icon-192.png` и `/icons/icon-512.png`. В текущем дереве репозитория каталога `public/` с этими ресурсами нет: для корректных иконок при установке PWA их нужно предоставить отдельно. Успешная сборка не проверяет наличие этих изображений.

## Gemini

В [`src/shared/api/gemini.ts`](src/shared/api/gemini.ts) есть функции текстового запроса, инсайта по последним записям настроения и ежедневной рефлексии. В текущих страницах вызовов этого модуля нет, поэтому AI не следует считать доступной функцией интерфейса.

Модуль использует модель `gemini-1.5-flash` и `VITE_GEMINI_API_KEY`. При интеграции проверьте доступность модели и квоты своего Google-проекта. Запрос выполняется из браузера, без серверного прокси; ключ доступен клиенту, а переданный контекст, включая заметки о настроении, отправляется Google.

Стратегия кэширования в service worker не гарантирует генерацию ответов без сети. AI-модуль не является терапевтом или медицинским инструментом.

## Развёртывание

1. Установите зависимости и задайте клиентские переменные окружения для production.
2. Выполните `npm run build`.
3. Разместите `dist/` на статическом хостинге. Для клиентских маршрутов настройте возврат `index.html`, например через `try_files $uri $uri/ /index.html` в nginx.
4. Запустите API отдельным Node.js-процессом с предварительно загруженным окружением и доступом к PostgreSQL.
5. На HTTPS-origin клиента проксируйте `/api/` к API, сохраняя префикс `/api/`. При такой схеме `VITE_SERVER_URL` можно оставить пустым. Не возвращайте SPA HTML для запросов API.
6. Настройте сертификат, перезапуск процесса, логи и резервное копирование БД средствами инфраструктуры.
7. Проверьте вход, создание записи, синхронизацию в другом браузере, прямое открытие вложенного маршрута и push-подписку.

Для локального просмотра production-клиента:

```sh
npm run build
npm run preview
```

Это не поднимает backend и не добавляет проксирование `/api`. Для одних только обычных API-запросов можно собрать клиент с явным `VITE_SERVER_URL`; для push всё равно нужен same-origin маршрут.

Сервер в текущей реализации разрешает CORS для любого origin. Перед публичным размещением ограничьте доступ на уровне инфраструктуры или измените серверную политику. Для напоминаний безопаснее один экземпляр планировщика: межпроцессной координации отправок нет.

## Проверки и разработка

```sh
npm run build
npm test -- --run
```

Сборка проверяет TypeScript и создаёт клиентский bundle и service worker. Vitest настроен на jsdom с `src/shared/test/setup.ts`; в текущем репозитории нет файлов `*.test.*` или `*.spec.*`. Поэтому однократный запуск сейчас завершается с кодом `1` и сообщением `No test files found`, а не подтверждает прохождение тестов.

При изменении синхронизации проверяйте локальное сохранение, отключение и восстановление сети, содержимое outbox и загрузку на другом устройстве. При изменении модели данных согласуйте типы, схему Dexie, хранилища, клиентский API, PostgreSQL-схему и серверные преобразования.

## Устранение проблем

| Симптом | Что проверить |
| --- | --- |
| Вход не проходит | API доступен, `VITE_SERVER_URL` указывает на нужный сервер, `AUTH_PASSWORD` совпадает, `JWT_SECRET` задан |
| API отвечает, но данные не синхронизируются | Подключение PostgreSQL, права роли, логи API и реальный `/api/sync`; одного `/health` недостаточно |
| `DATABASE_URL` задан, но подключение идёт не туда | Запуск через `node --env-file=server/.env server/index.js`; переменные окружения процесса имеют приоритет над dotenv |
| Запись видна только на одном устройстве | Outbox, сеть, срок JWT и ошибки API; локальное сохранение не доказывает успешную отправку |
| Push-запрос возвращает HTML или 404 | Same-origin прокси `/api`; push не использует `VITE_SERVER_URL` |
| Подписка не появляется | HTTPS/localhost, разрешения браузера, регистрация service worker, VAPID-ключи и доступность API |
| Напоминания не приходят после восстановления БД | Перезапустите API: scheduler не стартует автоматически после неудачной инициализации БД при запуске |
| Уведомления дублируются | Несколько API-процессов, рестарт, одновременные локальные таймеры и серверный push |
| После обновления старый интерфейс | Обновление service worker и кэша в DevTools; не очищайте IndexedDB без сохранения несинхронизированных данных |
| Вложенный URL возвращает 404 после перезагрузки | SPA fallback на статическом хостинге |
| Установленная PWA без иконки | Наличие файлов `/icons/icon-192.png` и `/icons/icon-512.png` на хостинге |

## Безопасность и резервные копии

- Не коммитьте `.env`, приватные ключи и дампы базы. `.env.example` предназначен для безопасных шаблонов без реальных секретов.
- JWT хранится в `localStorage` и доступен JavaScript на origin приложения. Клиентские маршруты сами по себе не защищают данные: авторизацию API проверяет сервер.
- Все вошедшие пользователи имеют доступ к одним данным. Не используйте текущую модель как многопользовательский сервис с изоляцией аккаунтов.
- Удаление токена при выходе не следует считать удалением локальных записей из IndexedDB. Учитывайте это на общих устройствах.
- Резервируйте PostgreSQL внешними средствами, например `pg_dump`, и регулярно проверяйте восстановление в отдельную базу. Встроенных backup/restore-команд нет.
- Копия PostgreSQL не включает локальные изменения, ещё находящиеся в outbox. Перед очисткой браузерного хранилища убедитесь в успешной синхронизации.
- После утечки секретов замените пароль входа, JWT-секрет и затронутые ключи; одной записи в `.gitignore` недостаточно для удаления секрета из истории Git.
